# Historical Access and trends

## Concepts

Design deep-dive. HistoryRead uses details such as ReadRawModifiedDetails for interval and result limit. Historizing indicates historical collection; AccessLevel.HistoryRead indicates read capability. An archive keeps Value, quality and timestamp of the source. A chart that accumulates samples in the browser does not demonstrate Historical Access.

## Experiment

Design a trend screen with historical and live temperature. The course server does not implement HistoryRead: a request must be treated as unsupported, not masked with data generated by the UI.

## In the C# code

Separate the storage of the simulation from the HistoryRead handler. Implement pagination with continuation points, explicit release and memory limits. For aggregates use declared capabilities and consistent semantics.

## Exercise and verification

Archive 1000 samples, read a window in pages of 100, verify order, duplicates and quality. Repeat a read after restarting the process and compare the timestamps.

## Mistake to avoid

SourceTimestamp and the time of insertion into the archive are not equivalent. Do not compute an average ignoring quality, missing intervals and the rules of the aggregate.

## Goals, prerequisites and availability

Estimated time: 2–3 hours. The initial server does not support Historical Access. This lesson provides the design of the provider, the client flow and the criteria to build the lab. A trend obtained by keeping notifications in the browser is not a demonstration of HistoryRead.

The minimum historical datum is a DataValue with Value, StatusCode and SourceTimestamp. Also keep acquisition/insertion times when needed, without substituting them for the date of the measurement.

## The contract of the node

Historizing indicates historical collection of the Variable; the HistoryRead bit in the access level describes the read capability. Declaring these fields without implementing the service deceives the client. User authorization and operation limits must also be consistent.

Choose raw history first. Modified history and aggregates have further rules and are not automatically covered by an SQL query on averages and timestamps.

## Guided client query

Snippet for a future server with history support; it requires an open Session and cannot run successfully against the current server:

```csharp
var details = new ReadRawModifiedDetails
{
    IsReadModified = false,
    StartTime = DateTime.UtcNow.AddMinutes(-10),
    EndTime = DateTime.UtcNow,
    NumValuesPerNode = 100,
    ReturnBounds = false
};
var nodes = new HistoryReadValueIdCollection
{
    new() { NodeId = Lessons.Id(session, "Reactor1.Temperature") }
};
session.HistoryRead(null, new ExtensionObject(details),
    TimestampsToReturn.Both, false, nodes,
    out var results, out var diagnostics);
```

For every HistoryReadResult check the StatusCode, decode HistoryData from its ExtensionObject and keep the ContinuationPoint. The continuation point is opaque: do not treat it as an SQL offset exposed by the protocol. To get the next page repeat the appropriate request with the token; if you interrupt the read, release it explicitly.

Do not assume that the page contains exactly 100 values: server limits, bounds and data availability can affect the result. An empty response with a valid status must be distinguished from a response in error.

## Server provider and storage

Separate three responsibilities: acquisition, persistence and the HistoryRead service. The simulation emits measurements; the archive stores them; the provider applies interval, ordering, limits and continuation.

A conceptual structure for the storage:

```csharp
public sealed record HistoricalSample(
    string NamespaceUri, string Identifier,
    DateTime SourceTimestamp, double Value, uint StatusCode);
```

This record is an internal choice, not a UA type to publish. For a source that produces several samples with the same timestamp also keep a stable ordering criterion. Pagination must not duplicate or skip rows because of equal timestamps.

## Solved exercise: incomplete window

You have 1000 samples, ten with Bad quality and an interval with no data. Can the chart draw a continuous line interpolating everything?

**Solution.** The archive keeps the original quality; the UI must distinguish gaps and invalid samples. An average that silently discards the Bad values changes the meaning of the indicator. For industrial aggregates implement the rules provided and declare the capabilities supported.

**Acceptance lab.** Request 100 samples per page until completion; compare count and order with the dataset inserted; interrupt halfway and release the token; repeat after a restart to verify persistence. Add two simultaneous reads to avoid a single shared global cursor.

The live part joins the trend with an explicit rule on the time boundary, so that the last historical sample is not duplicated by the first live one.
